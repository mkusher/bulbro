Network game protocol

Current browser and Bun server behavior as of 27 September 2026. This page describes the two-player network mode and distinguishes enforced rules from remaining limitations.

Overview

The browser creates a username-based identity with POST /api/users. The server returns an ID and a signed, 24-hour JWT containing id, authenticatedAt, and expires. Subsequent game HTTP requests use Authorization: Bearer <token>. The lobby WebSocket at /ws starts with {"type":"auth","token":"…"}; the server verifies the token and binds its ID to that socket. This is a server-issued anonymous identity, not a password or external account login.

The signing key comes from JWT_SECRET, or from a random value generated at server startup when that variable is absent. The browser keeps its token in memory. The server keeps lobbies and socket mappings in memory. Each lobby has one host, at most one guest, a players list with connection status, and an upserted readyPlayers list. The host creates the initial wave state and simulates world events. The guest simulates its own movement and applies host world events. The server validates and relays live messages but does not simulate the game or store authoritative wave state.

Scope: This mode requires exactly two distinct players to start. Each browser treats its own player as local and the other as remote. Live event and position messages share the schemas in @bulbro/network-protocol.

Lobby and game start

1. Create identitiesEach tab posts a username and receives its own user ID and JWT.
2. Create or joinThe host creates a lobby. The guest joins by lobby ID. The server returns the full lobby, including earlier ready selections.
3. Authenticate socketsEach tab sends its JWT over WebSocket. The server marks that known player connected and notifies the other tab.
4. Ready and startBoth members submit a Bulbro. The host sends initial state once both are connected and ready; the guest receives game-started.

Room creation and joining bind the supplied player ID to the bearer token. Joining a full room returns 409; an existing member may rejoin. Readiness requires membership and replaces any earlier selection by the same ID. A late joiner receives existing readiness in the HTTP lobby response. The client also merges readiness notifications by ID so a delayed response does not discard a newer selection.

The start route accepts only the host and requires two distinct room members, both ready and connected, with registered sockets. The initial state's two player IDs must match the room. Missing rooms return 404; unmet start conditions return 409; mismatched state IDs return 400. The host enters the game only after a successful HTTP response, and places its own player first for local controls even if the guest readied first.

On a socket close, the player stays in the room with status:"offline", and the other tab receives player-disconnected. A newly authenticated socket for that player changes the status to connected and sends player-connected. The lobby listener remains active during play, so the lobby and in-game views can show remote connection changes.

Live game flow

Host or guestSends an event batch or position update with a game ID and version.
Server relayValidates the shared wire schema, room membership, sender role, and position player ID.
Other playerReceives the message, merges role-filtered events or position, and continues local simulation.

The host's initial state arrives in the guest's game-started message. During play, each browser sends its queued events every 50 ms when the queue is nonempty. The host sends world events and its movement; the guest sends only its movement. Receiving a batch does not trigger an extra game tick or an automatic response. Position updates travel independently, nominally every 20 ms, with their own versions. The server forwards accepted messages to the other registered room player; a guest cannot send a host batch, a host cannot send a guest batch, and a position packet's playerId must equal the socket's verified ID.

The client chooses the remote control target by finding the room member whose ID differs from the local user ID. It applies accepted remote events to the current state without replaying already-applied local events, and reconstructs enemy and shot runtime objects after JSON transport. The server validates message shape, not individual game events or game physics.

Remaining gaps

JWTs establish a server-issued session ID, but anyone can create a new username-based identity. Room and socket state live only in this server process. The server does not provide authoritative simulation, replay, or recovery after a connection interruption.

OpenAutomatic reconnect and resync are absent.
