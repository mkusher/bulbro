Network game protocol

Current browser and Bun server behavior as of 2 October 2026. This page describes the two-player network mode and distinguishes enforced rules from remaining limitations.

Overview

The browser creates a username-based identity with POST /api/users. The server returns an ID and a signed, 24-hour JWT containing id, authenticatedAt, and expires. Subsequent game HTTP requests use Authorization: Bearer <token>. The lobby WebSocket at /ws starts with {"type":"auth","token":"…"}; the server verifies the token and binds its ID to that socket. This is a server-issued anonymous identity, not a password or external account login.

The signing key comes from JWT_SECRET, or from a random value generated at server startup when that variable is absent. The browser keeps its token in memory. The server keeps lobbies and socket mappings in memory. Each lobby has one host, at most one guest, a players list with connection status, and an upserted readyPlayers list. The host creates the initial wave state and simulates world events. The guest simulates its own movement and applies host world events. The server validates and relays live messages but does not simulate the game or store authoritative wave state.

Scope: This mode requires exactly two distinct players to start. Each browser treats its own player as local and the other as remote. Lobby payloads, lobby notifications, live updates, and next-wave messages share the schemas in @bulbro/network-protocol.

Lobby and game start

1. Create identitiesEach tab posts a username and receives its own user ID and JWT.
2. Create or joinThe host creates a lobby. The guest joins by lobby ID. The server returns the full lobby, including earlier ready selections.
3. Authenticate socketsEach tab sends its JWT over WebSocket. The server marks that known player connected and notifies the other tab.
4. Ready and startBoth members submit a Bulbro. The host sends initial state once both are connected and ready; the guest receives game-started.

Room creation and joining bind the supplied player ID to the bearer token. Joining a full room returns 409; an existing member may rejoin. Readiness requires membership and replaces any earlier selection by the same ID. A late joiner receives existing readiness in the HTTP lobby response. The client also merges readiness notifications by ID so a delayed response does not discard a newer selection.

The start route accepts only the host and requires two distinct room members, both ready and connected, with registered sockets. The initial state's two player IDs must match the room. Missing rooms return 404; unmet start conditions return 409; mismatched state IDs return 400. The host enters the game only after a successful HTTP response, and places its own player first for local controls even if the guest readied first.

On a socket close, the player stays in the room with status:"offline", and the other tab receives player-disconnected. A newly authenticated socket for that player changes the status to connected and sends player-connected. The lobby listener remains active during play, so the lobby and in-game views can show remote connection changes.

Live game flow

Host or guestSends an event batch or position update with a game ID and version.
Server relayValidates the shared wire schema, room membership, sender role, and position player ID.
Other playerReceives the message, merges role-filtered events or position, and continues local simulation.

The host's initial state arrives in the guest's game-started message. During play, each browser sends its queued events every 50 ms when the queue is nonempty. The host sends world events and its movement; the guest sends only its movement. Receiving a batch does not trigger an extra game tick or an automatic response. Position updates travel independently, at most every 20 ms when the position changes. The server forwards accepted messages to the other registered room player; a guest cannot send a host batch, a host cannot send a guest batch, and a position packet's playerId must equal the socket's verified ID.

Position packets carry a per-wave sender sequence in version, starting at 1. The receiver accepts the first packet of a wave and afterwards only packets with a higher sequence than the last applied one, so late packets are dropped. After the first position packet of a wave, event batches no longer move the remote player; its position comes only from position packets, which are sent whenever it changes. sentAt on both batches and position packets is the sender's Date.now() and is used only for diagnostics, never for ordering.

The client chooses the remote control target by finding the room member whose ID differs from the local user ID. It applies accepted remote events to the current state without replaying already-applied local events, and reconstructs enemy and shot runtime objects after JSON transport. The server validates message shape, not individual game events or game physics.

Shop and next wave

1. ShopAfter a won wave each browser shows its own shop. Purchases and re-rolls change only the local player's state.
2. ReadyThe Start button reads Ready. Pressing it locks the shop and sends next-wave-player-ready with the upcoming wave number and the local player's full post-shop state.
3. CollectThe server stores the latest state per member for that wave and relays the readiness message to the other member, whose shop shows the player as ready. Pressing Not Ready sends next-wave-player-not-ready; the server drops the stored state, relays the message, and the shop unlocks.
4. StartOnce every member is ready, marked connected, and has a registered socket, the server sends next-wave-started to everyone with all player states, host first.
5. SimulateEach browser applies the next wave to the host-first players, so start positions match, reorders local first for controls, and starts a fresh event and position sync.

The shop lists every lobby member with a connection badge, taken from player-connected and player-disconnected, and a readiness badge. Readiness counts only for the wave after the local current wave, so a message for another wave never marks a player ready.

The server accepts readiness only from a room member for its own ID, with player.id equal to the socket identity, and only for the wave after the last started wave. The host's POST /api/game/:id/start sets the last started wave to 1. Repeating readiness replaces the stored state. Withdrawn readiness follows the same membership and wave rules. After the wave starts, the server ignores it, so a Not Ready that loses the race still starts the wave. Starting a wave clears the stored readiness, so duplicate or stale messages cannot start it twice. When a member is offline, the wave waits; the server checks again when that member's socket authenticates. Clients cannot send next-wave-started; the server drops it. A client also ignores a start whose wave is not its current wave plus one.

Trust: The server checks the shape and the player ID of the submitted state, but not its contents. A modified client can report arbitrary materials or weapons, the same trust level as live event batches.

Message inventory

The gameplay protocol has five HTTP operations and fourteen WebSocket message types, plus untyped error replies. Payloads below omit the WebSocket type discriminator, which is required on every typed message. HTTP routes are relative to the deployed /api prefix; WebSocket JSON travels over /ws.

Schema ownership: Shared lobby schemas define Player, Weapon, Bulbro, ReadyPlayer, Lobby, and the seven-member LobbyWebsocketMessage union. Shared live schemas define the six-member WebsocketMessage union and re-export the lobby schemas. Both browser and server consume this package. HTTP envelopes and the auth schema remain server-local; error replies have no shared schema.

Shared lobby payloads

Weapon{id:string, name:string, classes:string[], statsBonus, shotSpeed:number}. All statsBonus fields are optional: numeric damage, cooldown, range, knockback, critChance, critMultiplier, and scaling with optional numeric meleeDamage, rangedDamage, elementalDamage.
Bulbro{id:string, name:string, statBonuses:Record<string,string|number|boolean>, style:{faceType:string,wearingItems:unknown[]}, weapons:Weapon[]}.

These schemas preserve additional fields. For example, character weapon choices and weapon attack definitions survive JSON transport. The shared weapon schema accepts nested numeric damage scaling, including the default SMG's scaling:{rangedDamage:0.5}; malformed scaling values fail readiness validation.

In live and next-wave messages, gameId and playerId are strings; version, sentAt, and serverStartTime are numbers. Timestamps are epoch milliseconds. Only wave is constrained to an integer by the shared schema. Next-wave player objects require an id:string and retain the remaining serialized state without validating its internals.

Error replies

HTTP failures use {error:string} with an appropriate status: 400 for invalid input, 401 for missing/invalid authentication, 403 for identity or role mismatch, 404 for a missing lobby, and 409 for a full lobby or unmet start conditions.

WebSocket errors are untyped {error:string} objects: Invalid message, Unauthorized, Already authenticated, Session expired, or Internal error. Sessions close on expiration. Rejected live messages can be silently dropped rather than acknowledged with an error. The lobby listener ignores messages outside its union; the in-game listener logs unknown messages.

Remaining gaps

JWTs establish a server-issued session ID, but anyone can create a new username-based identity. Room and socket state live only in this server process. The server does not provide authoritative simulation, replay, or recovery after a connection interruption.
