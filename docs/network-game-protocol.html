Network game protocol

Implementation review of the browser client and Bun server, as of 27 September 2026. This describes the code as written, including messages that currently fail validation.

Overview

The browser uses JSON over HTTP at /api/ to create a user, create or join a lobby, report readiness, and start a game. It opens one WebSocket at /ws per lobby connection, sends {"type":"auth","userId":"…"}, and reuses that socket for lobby notifications and game traffic. The server holds lobbies and user-to-socket mappings in process memory. It relays live messages; it does not simulate the game or keep an authoritative wave state.

The host creates the initial WaveState and sends it via HTTP. Each browser then simulates a local wave. Live synchronization uses alternating host and guest event batches, plus independent position messages. The client filters and applies events by role. Both sides now use the same event-batch schema from @bulbro/network-protocol.

Scope: The UI assumes one host and one guest. The registry accepts an arbitrary number of players, while game startup and state processing select a single remote player.

Lobby and game start

Join and readiness notifications go to other players with registered sockets. The HTTP caller receives the lobby response. On game start, only non-host sockets receive game-started; the host proceeds locally after its HTTP call. serverStartTime and the full lobby are sent to the guest but are not consumed by its lobby message schema.

Live game flow

At wave start the host sends the first event batch. A receiver rejects old versions, flushes queued local events, applies role-filtered local and remote events, ticks its wave, and sends the next version. Position updates are produced by a throttled signal, nominally every 20 ms, with a separate sequence counter. The client tries to preserve its own player and shots while merging remote changes.

Shared wire shape: Both event-batch messages require gameId, version, events: object[], and sentAt. Position messages use the same package. The server validates and relays these messages but still does not inspect individual game events or maintain an authoritative game state.

Potential gaps and recommended fixes

Resolved: The live event-batch schema mismatch was fixed by moving the wire definitions into @bulbro/network-protocol. A server relay test checks both host-to-guest and guest-to-host event delivery.

PriorityFinding and impactSuggested fix
HighIdentity and role are assertions from the caller. WebSocket auth trusts any userId; HTTP has no authentication; relay infers sender from message type or playerId, without checking the bound socket or lobby membership. A caller can impersonate a player, start a lobby's game, or inject updates. Socket registration · Relay · HTTP routesIssue a server-verifiable session credential; bind it to the socket; authorize each operation against membership and host role.
HighReady state is incomplete and unbounded. markReady appends duplicates and accepts an ID absent from players. Existing readyPlayers is returned in HTTP lobby responses but omitted from the client lobby schema, so a late joiner misses earlier readiness. The start route does not check both players are ready. Registry · Client lobby schemaRequire lobby membership, upsert by player ID, include ready players in client state, and enforce start preconditions server-side.
HighTwo-player assumptions are not enforced. The server accepts more players, but NetworkGameConnection picks the first non-host with a non-null assertion, and StateUpdater merges exactly one remote player. A solo host or third player can break or diverge. Registry · Game connectionEnforce exactly two participants for this mode, or extend the client model to support all participants.
HighGuest remote control targets the guest ID. Both roles set remotePlayerId to the first non-host. For the guest, that is its own ID; host movement events therefore do not update the guest's remote direction control. Game connection · Remote controlSelect the player whose ID differs from the local user's ID.
MediumFirst position packet is discarded. The sender starts position versions at 0; StateUpdater initializes lastPositionVersion to 0 and rejects versions less than or equal to it. Sender · ReceiverInitialize the receiver to -1 or start the sender at 1.
MediumPosition freshness compares unrelated clocks. Position sentAt uses the sender's elapsed wave time, while the receiver compares it with its own elapsed wave time. Different start times can suppress valid positions. Event batches use Date.now(); once one is processed, its epoch timestamp makes later elapsed-time position packets appear stale. Sender · ReceiverUse per-sender sequence numbers for ordering; define timestamps in one clock domain if needed for diagnostics.
MediumReconnect and close handling can lose the active socket. Reconnect is not invoked by the game flow. Reauth for the same ID replaces byUser, but closing the old socket removes the ID's new mapping; old mappings can also remain when one socket authenticates as another ID. Offline status has no matching online restoration. Client socket · Server socket mapRemove mappings only if they still point to the closing socket; define reconnect, reauth, resync, and online transitions.
MediumEvent delivery has no recovery. Events are flushed before the asynchronous send; no acknowledgement, retry, snapshot, or replay path is used. A dropped socket or malformed batch can strand the ping-pong loop and lose events. State sync · Event queueAdd acknowledged sequence numbers, buffered resend, and a snapshot/resync path after interruption.
MediumHTTP success can hide a missing game. startGame, hostUpdate, and playerUpdate return without an error when the lobby does not exist; routes still return success. The host checks only the HTTP call's completion, not res.ok. Server controller · Client startReturn explicit 404/409 responses and make the host await and check a successful start before moving to the game screen.

These are code-review findings, not runtime measurements. The first-position version mismatch follows directly from the counters. Other failure modes depend on timing or caller behavior and should be confirmed with end-to-end tests when fixed.
